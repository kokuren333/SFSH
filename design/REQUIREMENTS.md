## 0. 最上位制約と設計原則（全節に優先する）

### 0.1 最上位制約（緩和不可）

| ID | 制約 | 根拠 |
|---|---|---|
| **C-2** | **原作の文章・台詞・画像を再利用しない**（コマ・映像・音声・歌詞を含む）。引用ゼロを既定とする（作品名・人名・用語などの固有名は可）。**権利面で守る核はこの1つだけ。** | BRIEF 1, 3.6, 11 |
| C-8 | **サイト用**の公開リポジトリに出すのはビルド済みサイトのみ。ハーネス本体・調査中間データ・秘密情報は出さない。（権利ではなく情報境界の制約）**（v1.5・A08）** ハーネス本体（コードと設計文書）は別の公開リポジトリとして公開する（6.6）。そこにも調査データ・NKG・生成物・台帳・ハンドオフ文書・秘密情報は出さない。 | BRIEF 0, 6, 13 |

### 0.2 設計原則 P-1「ゲートで創造性を落とさない」[決定・A06]

1. **止めてよいのは、客観的に機械判定できる実害だけ**: (a) 原作テキスト・画像の混入検出（5.1）／(b) 秘密情報・非公開データの流出（6.3-4）／(c) スキーマ・ビルドの破損。
2. それ以外の懸念はすべて **advisory（助言）**。表示して記録するが、通過／停止を決めない（5.2）。
3. **迷ったら作る側に倒す。**
4. 問題は公開前に予防しきろうとせず、**公開後の取り下げで受ける**（5.4）。そのために「いつでも速く取り下げられること」を基盤として維持する。
5. 人手承認・LLM の判定・数値上限を停止条件にしない。新しい停止条件を足す提案は、1 の実害に当たることを示して PM の承認を得る。

### 0.3 中核思想と制作指針（方向づけ。停止条件ではない）

| ID | 指針 | 根拠 |
|---|---|---|
| C-1 | SFSH が作るのは「物語の認知モデル」。何が起きたか／誰が何を望みどう変わったか／なぜその展開か／なぜ面白いか の4点に答える構造と独自分析で構成する。 | BRIEF 1 |
| C-3 | 出来事を場面順に網羅せず、人物・因果・テーマへ抽象化する。スキーマに「場面」「台詞」「コマ」の型を持たない。件数・文字数は目安（2.4）。**（v1.7・A11）例外**: 作品ページの「あらすじ（全編・ネタバレ）」は、NKG の事実層から冒頭から結末までを時系列に語り直す要約のページとする（3.2）。場面・台詞の再現はしない。スキーマに場面・台詞の型を持たない点は変わらない。 | BRIEF 3.6, 3.4, 14（A11） |
| C-4 | 生成の中心は独自の分析・比較・批評。 | BRIEF 3.6 |
| C-6 | 作品ごとに出典・生成履歴・公開状態を台帳管理し、いつでも差し止め・取り下げできる（P-1-4 の基盤）。 | BRIEF 3.6, 2-7 |
| C-7 | 全ノードに出典と信頼度を付ける。情報不足は埋めずに「不明」として残す。モデルの記憶だけを根拠にしたノードは公開射影に入れない（要素単位の品質規則。作品は止めない）。 | BRIEF 2-2, 3.5 |

- **廃止（v1.2）**: C-5（公開前に機械＋人手の権利ゲートを必ず通す）、C-9（グラフと生成文の両方をゲート対象にする）。
- 迷ったときの判断: 作る側に倒す。不採用にするのは **C-2 に触れる提案だけ**。

## 1. システム全体アーキテクチャ

### 1.1 パイプライン [決定]

```
[Discord bot]──┐
               ├─▶ S0 受付 ─▶ S1 調査 ─▶ S2 NKG構築 ─▶ S3 生成 ─▶ S4 自動確認 ─▶ S5 静的ビルド ─▶ S6 公開
[Muse / CLI]───┘    (queue)    (sources)   (nkg.json)   (pages)    (止めない)     (dist/)        (siteのみpush)
                                    ▲──────────── 相互チェック（Luna⇄Haiku）────────────▲
```

| 段 | 入力 | 処理 | 出力（`works/<work_id>/` 配下） | 主担当 |
|---|---|---|---|---|
| S0 受付 | 指示（作品名＋範囲。単発または一覧ファイル 4.5） | 構文正規化・同定調査による正式名称の確定（4.6）・重複判定・キュー投入 | `queue/*/<job_id>.json`, `queue/batches/<batch_id>/` | 決定的コード（同定調査の候補抽出のみ Luna） |
| S1 調査 | JobRequest | 粗筋枠の検索→分析枠の検索→取得→出典カード化→主張(claim)抽出→カバレッジ計測と不足だけを狙う追加調査（v1.8・A12。S2 の事実層の後にもう一度） | `research/sources.json`, `research/claims.json`, `research/coverage.json`, `research/raw/`（非公開） | Luna 作成／Haiku レビュー。本文の取得・保存は決定的コード（1.3 取得経路）。カバレッジの計測は決定的コード |
| S2 NKG構築 | claims | モジュール選択→ノード/エッジ生成→検証 | `nkg/nkg.json`, `nkg/validation.json` | 事実層=Luna、解釈層=Haiku、相互レビュー（3.2） |
| S3 生成 | nkg.json | 公開射影→ページ用テキスト・可視化データ生成 | `gen/public.json`, `gen/pages/*.json`（v1.7: `synopsis.json` を含む） | 本文=Haiku 執筆／Luna レビュー＋決定的レンダラ |
| S4 自動確認 | gen 一式 | 原作テキスト・画像の混入検出（該当箇所のみ修正）と advisory の記録（5.1・5.2）。作品は止めない | `check/report.json` | 決定的コード |
| S5 ビルド | Public の作品 | 静的サイト生成 | `site/dist/` | 決定的コード |
| S6 公開 | dist | 事前検証→公開リポジトリへ snapshot push | 公開リポジトリ, `releases/<release_id>.json` | 決定的コード（サイト開設後は自動。5.3） |

### 1.2 構造上の決定 [決定]

1. **2リポジトリ構成**。ハーネスの作業リポジトリ（本フォルダ。ローカルのみ・remote なし）と、公開の「サイト」リポジトリを物理的に分ける。サイト用リポジトリは `site/dist/` の中身だけを受け取る（第6節）。**（v1.5・A08）** ハーネス本体は、作業リポジトリの remote にせず、許可リストで書き出した写しを3つ目の公開リポジトリへ出す（6.6）。
2. **ファイルベース**。DB を持たない。段ごとの成果物を JSON ファイルで残し、各段は前段のファイルだけを入力にする。どの段からでも再実行できる（チェックポイント再開）。
3. **LLM は「中身」を作り、コードは「形と関門」を作る**。スキーマ検証、目安の集計、類似度計算、公開射影、ビルド、push 可否判定は決定的コードで行い、LLM に判定を委ねない。
4. **モデル呼び出しは `ModelPort` 抽象の背後に置く**。実装は2つ（Haiku 系／Luna 系）。入出力は JSON スキーマ固定、全呼び出しを `logs/calls/` にプロンプトハッシュ・モデルID・トークン・所要時間つきで記録する。呼び出し経路は **CLI ヘッドレス**（M0 V-4、CP-014）。経路は `ModelPort` の実装差し替えで変えられるように保つ（運用段階の API 移行は U-02）。
5. **worker は1プロセス、ジョブは並行**（v1.9・A13。v1.8 までは「単一ワーカー・同時実行1」）。worker プロセスは1つだけ（`queue/worker.lock`）で、その中で最大 N 件（既定3、`harness/config/worker.json`）のジョブを並行に処理する。共有するもの（キューの状態・サイトのビルド・公開）だけを直列化する（4.4「並行実行」）。v1 は本機（Windows 11）上のローカル実行。
6. **原作本体は取り込まない**。入力は公開ウェブ上の二次情報と公式の周辺情報のみ（1.3）。原作の全文・スキャン・字幕・台本を取得・保存・モデル入力する経路を作らない。
7. **実装言語は TypeScript（Node）単一を推奨**、SSG と可視化ライブラリはオーケストレーターが M0 で選定し台帳に記録する。条件: 完全静的出力、外部 CDN・外部トラッカー・外部画像のホットリンクなし（依存はビルドに同梱）。

### 1.3 調査（S1）の要件 [決定]

- 出典ティア（信頼度の基礎値。2.3 で使用）:

| ティア | 例 | 扱い |
|---|---|---|
| T1 公式 | 出版社・製作委員会・公式サイト・作者公式発信・書誌DB（国会図書館等） | 事実の最優先根拠 |
| T2 専門 | 新聞・専門誌・学術・受賞機関・署名入り批評 | 事実および受容・批評の根拠 |
| T3 編集型 | 百科事典型サイト（Wikipedia 等） | 事実の補助。ライセンス表示義務を出典カードに記録 |
| T4 ファン | ファンwiki・個人ブログ・感想サイト | 単独では事実の根拠にしない。受容・考察の根拠としてのみ |
| T5 匿名 | 掲示板・SNS 断片 | 「ファンの考察」の存在証明としてのみ |
| 禁止 | 海賊版・違法アップロード・リーク・原作全文転載・ペイウォール回避・robots.txt/利用規約が自動取得を禁じるサイト | 取得しない。ドメイン denylist を持つ |

- 出典カードに保存するのは: URL、題名、発行者、ティア、ライセンス、取得日時、内容ハッシュ、検証用の短い抜粋 [暫定: 1出典あたり合計400字以内]。抜粋は非公開領域のみに置き、公開物へ流さない。
- 二次情報のあらすじ・解説にも著作権がある前提で扱う。モデルへの指示は常に「事実・関係・因果を自分の言葉で主張(claim)に分解せよ。出典の文を写すな」。
- 1ジョブの予算上限を持つ [暫定: 検索40回・取得60ページ・壁時計30分・モデル呼び出し総額は U-13]。超過時は打ち切り、得られた範囲で進め、欠落を「情報不足」として記録する。**（v1.4）** 壁時計30分は調査の検索・取得に対する打ち切りで、ジョブ全体の所要時間の目標（7.3）とは別。取得回数の数え方は台帳 CP-025 を正とする。モデル呼び出し総額は目安であり、超過は advisory として記録・通知するだけで打ち切らない（U-13、P-1-5）。
- **取得経路 [決定・v1.3。M0 V-3 の実測に基づく]**: モデル側のツール（web_search／open_page）による取得は提供元の側で行われ、robots・denylist・予算を SFSH から強制できない。そのため強制が要る部分を決定的コードに置く。
  1. **検索と候補選定 = Luna の web_search**。候補 URL は実行イベント（JSONL の web_search 結果）から決定的に採る。イベントにも指示入力にも無い URL（モデルの自己申告だけの URL）は候補にしない。検索回数はイベント数で数える。
  2. **本文の取得・保存 = 決定的コードのフェッチャ**。取得前に denylist と robots.txt を照合し、予算（取得ページ数）を数える。出典カード（URL・取得日時・内容ハッシュ・抜粋）を作るのはフェッチャだけ。
  3. **claim 抽出 = Luna**。入力は保存済みの抜粋。claim の根拠にできるのは出典カードのある出典だけ（検索結果のスニペットと open_page の読み取りは、それ単独では根拠にしない）。
  4. **open_page は補助**。フェッチャで本文を取れなかったページ（動的ページ等）の内容確認に限り、denylist・robots 照合済みの URL をハーネスが渡す呼び出しでのみ使う。取得予算に数える。照合済みでない URL への open_page がイベントに現れたら、ジョブ台帳に記録して advisory に出す（ジョブは止めない）。
  5. denylist・robots・予算で取得しなかった URL は、その URL を飛ばすだけでジョブを止めない。欠落は「情報不足」として記録する（新しい停止条件ではない。P-1）。
- 十分性判定: 選択されたモジュールごとに「根拠 claim が閾値以上あるか」を決定的に数える。不足モジュールは生成せず、ページに「この観点は情報不足のため未掲載」と表示する。

#### 調査段の強化（v1.8・AMENDMENT 12）[決定。数値は暫定]

目的: 調査を「そこそこ集まったら止める」から「作品全体を覆うカバレッジ目標を満たすまで、予算の範囲で続ける」に変える。物語そのもの（出来事の連なり）の素材を、分析・評論の素材とは別枠で厚く集める。

1. **段の構成**: S0 → **粗筋枠の検索（`search_plot`）** → 分析枠の検索（`search_r1`）→ claim 抽出 → **追加調査（`followup`、claim のカバレッジ）** → claim 査読 → モジュール選択 → フェーズ → 事実層 → **不足検出と追加調査（`gapfill`、事実層のカバレッジ）** → **作り直し（`refact`、gapfill で claim が増えたときモジュール選択・フェーズ・事実層を作り直す）** → 解釈層 → 以降。キューの状態は gapfill／refact を「構造化中」とする。
2. **粗筋枠**: 公式の STORY・各話／各章ガイド、出版社・配給の作品紹介、百科事典型のあらすじ節・各話リスト、作品データベースのあらすじなど、出来事レベルの事実を扱う出典を狙う専用の検索（物語全体の呼び出し＋結末・中盤の区間の呼び出し）。選んだ候補には観点 `plot` を付け、claim 抽出は「1件1出来事・時系列・結末まで・話数／章番号」の指示で行う。ティアの優先（T1 > T2 > T3、T4 は足りない区間に限って少数）と除外ページ（台詞・脚本・字幕の書き起こし、全文転載、海賊版等）は従来どおり。
3. **claim の項目の追加**: 観点 `plot`（粗筋の出来事）、`story_unit`（出典に明記された話数・章番号。無ければ null）、`characters`（関わる人物名）。自分の言葉で書く規則・evidence の照合・30字ガード・C-2 は不変（出典の文の写しは素材にしない。要約としての事実は集めてよい）。
4. **カバレッジ目標**（決定的に数える。満たさない項目 = 1つの追加調査の的）:

| 対象 | 目標 [暫定] |
|---|---|
| 時系列の全区間 | 粗筋 claim が 序盤 ≥6・中盤 ≥8・終盤 ≥6（phase_hint、または story_unit の位置で区間を決める） |
| 話数・章の単位 | 単位数が分かる作品（書誌 claim の「全N話／章」、または story_unit が3種以上）は、各単位に粗筋 claim ≥1。欠けた単位は連続区間ごとに的にする（後ろの単位から） |
| 主要人物の動き | claim の characters の出現上位6人（3件以上）それぞれに、粗筋 claim ≥3 と、終盤の状態が分かる claim（終盤・結末・M07・M02）≥1 |
| 結末部 | 結末（spoiler ending）の canon claim ≥4、M02 の canon claim ≥1 |
| 事実層（gapfill） | 各フェーズの出来事 ≥3、最後のフェーズの出来事 ≥3 と結末の出来事 ≥1、主要人物（上位6人）が出てくる出来事 ≥2 |
| 分析枠 | 常時モジュールの有効 claim ≥3（1.3 十分性と同じ閾値）、査読の missing（gapfill で的にする） |

5. **追加調査のループ**: 的ごとに狭い Luna web_search（検索2・選択6）を並行（同時3）で行い、優先順（結末 → 区間・単位 → 人物。分析枠の的を1〜2件差し込む）に取得（的あたり GET 4）し、新しい出典だけ claim を抽出する（不足の言葉を focus として渡す）。followup は「目標未達・枠の残りあり・研究の壁時計の残りが 20 分以上（gapfill の取得時間を残す）」の間 最大3回、gapfill は最大2回（壁時計の残り3分以上）。新しい claim が0の回で止める。gapfill の新しい claim は査読（最大2往復）してから使う。
6. **枠ごとの配分**（上限 40/60 の内側。上限は変えない）: 粗筋枠 検索 ≤12・取得 ≤22（後段のため 18／22 を残す）、分析枠 検索 ≤10・取得 ≤14（10／12 を残す）、followup は gapfill のため 8／10 を残す、gapfill は残り全部。取得は GET 数で数え、枠の上限で渡さなかった候補は fetch_log に記録しない（後段で選び直せる）。ジョブ全体の取得予算が尽きたときだけ従来どおり budget_exceeded と情報不足を記録する。配分は試験用に差し替えられる（`OPEN_FRAMES`）。
7. **予算**: 検索40・取得60・壁時計30分は上限のまま。目標に届かない項目は、最後に `research/gaps.json` へ `coverage_shortfall` として記録し、作品は止めない（P-1）。上限自体の変更は発注者の判断。
8. **記録**: 計測（detect）と追加調査の回（round: 的・検索数・選択数・取得数・GET 数・新しい出典・新しい claim・予算・止まった理由）を `research/coverage.json` に追記する。台帳には作品ごとの検出結果と回数・使用量を実測で書く。
9. **再調査**: 既存作品は `sfsh job rework <work_id>` で、`research/`・`nkg/` を `works/<id>/_rework-backup-<時刻>/` へ移し（`gen/` は複写。git 管理外）、同定済みの新しいジョブ（予算は新規）として一から集め直す。

## 2. Narrative Knowledge Graph（NKG）スキーマ仕様

### 2.1 基本方針 [決定]

- 1作品 = 1ファイル `nkg/nkg.json`（`schema_version` 必須）。JSON Schema を `harness/schema/` に置き、検証を通らない NKG は次段へ進めない。
- **全ノード・全エッジが共通の `meta` を持つ**（2.3）。`meta` を欠く要素はスキーマ違反。
- 文章フィールドはすべて自分の言葉による抽象記述とする。長さは目安 [暫定: `label` 40字、`summary` 160字、`analysis` 400字] で、超過は警告のみ（P-1）。
- 「場面」「台詞」「描写」「コマ」「カット」を表す型・フィールドは存在しない（C-3）。原文・台詞を格納する型は追加しない（C-2）。それ以外の型追加はオーケストレーターが決めて台帳に記録する。
- 物語の進行は **フェーズ**（作品ごとに3〜7個、最低「序盤／中盤／結末」）で表す。時点を持つ要素はフェーズ単位で持ち、場面単位にしない。

### 2.2 トップレベル構造 [決定]

```jsonc
{
  "schema_version": "1.0",
  "work": {
    "work_id": "", "title": "", "title_alt": [], "creators": [], "medium": "novel|manga|anime|film|drama|game|other",
    "bibliographic": { "publisher": "", "first_release": "", "status": "completed|ongoing|unknown", "source_ids": [] },
    "genres": [], "coverage": [ { "unit": "volume|episode|arc|season|whole", "from": 1, "to": 3, "label": "" } ],
    "publish_mode": "Public",              // Public（既定）| Restricted（5.3）
    "rights": { "state": "", "copyright_status": "in_copyright|public_domain|unknown", "holder_policy_note": "", "source_ids": [] },
    "module_selection": [ { "module": "M01", "weight": 0.0, "enabled": true, "reason": "" } ],
    "phases": [ { "id": "ph1", "label": "序盤", "order": 1 } ]
  },
  "sources": [],        // 出典カード（1.3）。抜粋本文はここに入れず research/ 側に置く
  "nodes": [], "edges": [],
  "gaps": [ { "module": "M05", "what": "", "reason": "insufficient_sources|conflicting_sources|out_of_coverage" } ]
}
```

`work.title` は正本題名（4.6）の写し、`work.title_alt` は出典で裏づけた別名のみとする。入力表記のエイリアスは `work.json` に持ち、NKG には入れない。

### 2.3 共通メタ（出典・信頼度・認識区分）[決定]

```jsonc
"meta": {
  "provenance": [ { "source_id": "s012", "locator": "節・見出し等", "support": "direct|inferred" } ],  // 1件以上必須
  "confidence": { "score": 0.0, "grade": "A|B|C|D", "basis": "計算根拠の要約" },
  "epistemic": "canon|consensus|fan_theory|sfsh_analysis",
  "coverage_ref": "どの範囲に属するか", "phase_ref": "ph2",
  "spoiler": "none|mid|ending",
  "authored_by": "haiku|luna", "reviewed_by": "haiku|luna", "review": "agreed|revised|disputed"
}
```

- **信頼度は決定的に計算する**（LLM の自己申告を使わない）: A = T1 が1件以上、または独立した T2 が2件以上／B = T2 が1件、または独立した T3 が2件以上／C = T3 が1件、または T4 が2件以上／D = それ以下。相互レビューが `disputed` なら1段階下げる。
- **公開条件**: `epistemic=canon` は B 以上、`consensus` は C 以上、`fan_theory` は出典の存在のみ必須（「考察」と明示して表示）、`sfsh_analysis` は根拠ノード（`based_on`）が公開条件を満たすこと。満たさない要素は公開射影から除外し `gaps` に落とす。
- `provenance` が空、または根拠が「モデルの記憶」のみの要素は生成時点で棄却する（C-7）。
- `epistemic` の4区分が BRIEF 3.5「誤解・解釈の分岐」の実体であり、サイト上で常に色／ラベルで区別表示する。

### 2.4 12モジュールとの対応 [決定]

| ID | モジュール（BRIEF 3.1） | ノード型 | エッジ型／主要フィールド | 既定 | 目安 [暫定] |
|---|---|---|---|---|---|
| M01 | ①人物関係グラフ | `Character`, `Faction` | `Relation{from,to,kind,valence,phase_from,phase_to,changed_by(event)}` — 関係は**フェーズ区間つき**で持ち、変化の原因イベントを指す | 常時 | 人物30 |

  - 「〜と読める」「〜と考えられる」等の機械的なヘッジは 1ページ 2回までにし、表現に変化を持たせる。事実層（canon）と解釈層（sfsh_analysis）の区別は、ブロックの認識区分に加えて文の書き方でも示す。C-2（原文・台詞・画像の不使用）、based_on 必須（C-7）、30字ガード、copied_phrase の削除は従来どおり。
  - 書き方は目安であり、超過・不足で削ったり落としたりしない（P-1）。分量・長い段落・ヘッジ回数は `gen/write_report.json` の `prose_spec` に決定的に記録する（advisory）。執筆は部分ごとの並行呼び出し（概要・図の本文・クイズ／核心ページごと）で行い、レビュー（Luna、最大2ラウンド）は全ブロックをまとめて行う。
  - カード・チップは入口とナビゲーション（作品ページの本質ページ導線、作品情報、一覧、関連ページ）に限定し、本文はカードの枠で囲まずに表示する（6.4）。既存作品の書き直しは `sfsh regen <work_id>`（S3 write → compose → S4 autocheck、検索・取得 0）で行う。
- **S3 あらすじ（全編・ネタバレ）（v1.7・AMENDMENT 11）** [決定]: 作品ページの本文の中心に置く、物語全体が分かる長編のあらすじ。S3 write 段の新しいページ種別として、既存ページの執筆と並行に書く（実装 `harness/src/gen/synopsis.ts`・`synopsisPrompts.ts`）。
  - 内容: 冒頭から結末までの時系列（events の story_order と phases の順）の語り直し。導入（目安 300〜400字）＋章立て（5〜12章。アーク／話数／フェーズの区切りで分け、各章に見出し、章内は 1〜3 節の小見出し。各章の目安 600〜1,400字）。結末まで明かす。表は使わない。
  - 分量の目安は作品の規模に応じて 8,000〜15,000字（映画 8,000〜10,000／全13話以下・小説 9,000〜12,000／全26話以下 11,000〜14,000／それ以上 12,000〜15,000）。**目安であり、素材にない細部で埋めない**。不足・超過は `gen/synopsis_report.json` に advisory として記録し、削ったり止めたりしない（P-1）。
  - 素材: 公開射影の事実層（出来事〔因果の連鎖つき〕・人物・関係・動機・変容・世界のルール・伏線・感情の動き・秘密・結末と直接原因）と、作品の有効な canon クレーム（書誌・題名・ジャンル・受容だけのものは除く。抜粋は渡さない）。`analysis` 欄とテーマ／文脈／解釈の項目（解釈層）は渡さない。**再調査はしない**（検索・取得 0）。根拠のない細部は書かない。based_on には事実層の公開要素 ID だけを残し、根拠が無くなったブロックは落とす（C-7）。
  - 書き方: 人物は一覧にせず、初めて登場する場面で名前・立場・関係を文中で紹介する（2回目以降は名前だけ）。原文・台詞の引用なし、会話の再現なし、場面描写の再現なし（要約としての語り直し。C-2）。解釈・考察・評価・テーマ論は混ぜない（事実層の散文。解釈は解釈ページが担う）。文体は全文です・ます調。段落は執筆仕様 v2 と同じ（2〜5文・目安 80〜250字、300字超は分ける）。小見出しは 20字以内。
  - 手順: (1) Haiku が章立ての計画と導入を 1 呼び出しで作る → (2) 章ごとに並行で書く（各章には割り当てた出来事と、それに結びつく動機・変容・ルール・関係・伏線・感情・クレームを「この章の素材」として渡す。紹介済みの人物と他章の出来事を示して重複を避ける）→ (3) 文末のです・ます率が 0.8 未満のブロックだけを文体のみ整える（1 呼び出し、査読の前）→ (4) Luna が全ブロックを査読（指摘のみ。時系列の語り直し自体は too_concrete にせず、解釈の混入は misclassified）、Haiku が改訂、最大2ラウンド → (5) 未解決の copied_phrase のブロックを削除、30字ガード（書き直し1回、なお一致する文は削除）、based_on の絞り込み → (6) 字数・章ごとの字数・段落・解釈語・文体を `gen/synopsis_report.json` に記録。査読の記録は `gen/reviews/synopsis.json`、本文は `gen/pages/synopsis.json`（ブロック＋章の順序）。A-1／A-2（S4・公開前検証）は `pages` 配下の全文字列が対象なので、あらすじも同じく検査される。
  - 書き直し: `sfsh regen <work_id> --parts synopsis` であらすじだけを書き直せる（`--parts pages` は既存ページだけ。省略時は両方）。
  - 既知の限界（v1.7 の実測、CP-057）: 既存3作品の素材（公開の出来事 7〜10件、有効クレーム 67〜151件）からは 4,000〜5,400字にとどまった。素材の上限による不足で、水増しはしていない。調査に無い結末（例: まどか☆マギカの最終話の結末）はあらすじにも書かれない。
- **前提リスクの実測結果（M0 V-3、CP-009・CP-014）**: Luna 系は非対話実行でウェブ検索とページ取得ができる（返却 URL 7/7 実在）。能力は足りるが、モデル側ツールでは robots・denylist・予算を強制できない。よって v1.2 で第一候補としていた「取得は決定的コードのフェッチャ、検索計画と claim 抽出は Luna」を採用した（1.3 取得経路）。作成 = Luna／レビュー = Haiku の分担は変わらない。

### 3.3 相互チェックの組み込み [決定]

1. **レビューは指摘のみ**。レビュー側は成果物を書き換えず、`findings[]{target_id, type, severity, evidence}` を返す。type は `unsupported`（出典が支持しない）／`overreach`（推論過剰）／`too_concrete`（場面再現に近い）／`copied_phrase`（出典・原作の言い回し）／`misclassified`（epistemic 区分誤り）／`missing`／`contradiction`。
2. 作成側が修正 → 再レビュー。**最大2往復**。未解決は `review: disputed` とし、信頼度を1段下げる。未解決の **`copied_phrase` だけは当該要素を削除**する（C-2）。`too_concrete` ほかは削除せず advisory に回す（5.2）。
3. 両モデルが一致していても、出典のない要素は C-7 により公開射影から除く。
4. 指摘件数・往復数・削除数を作品台帳に記録し、M2／M6 で品質指標として使う。
5. **撤去（v1.2）**: 権利ゲート用の独立二重判定、「判定が割れたら厳しい方を採用」、人手承認との連結。レビューは品質のための工程であり、公開可否の判定ではない。
6. **往復数の運用（v1.8・A12）**: 往復は「最大2」の範囲で運用する。ジョブ初回の事実層・解釈層は2往復。gapfill の後の事実層の作り直し（`refact`）は1往復（作業単位に収めるため）。実行ごとに `job resume … --review-rounds 1|2` で S2 の往復数を指定でき、使った往復数は台帳に作品ごとに記録する。
7. **S2 の作成の補助（v1.8・A12）**: 作成プロンプトでは claim ごとに出典の最上位ティアを示し、claim_refs には支える claim を漏れなく（目安3〜8件）、別の出典・上位ティアを優先して併記させる（信頼度 2.3 は引用 claim の出典から決まるため）。群の出力に、その型の claim が3件以上あるのに0件の型、または出来事2件以上で因果0・人物2人以上で関係0・秘密ありで Knows 0 があれば、その群だけ1回聞き直し、欠けの少ない方を採る（決定的な判定、停止条件ではない）。事実層は events →（people ‖ world）、解釈層は（逆算 ‖ 動機と変容 ‖ テーマと感情）→ extras の順に、同じ段の群を並行に作る。
8. **往復の内側の並行（v2.0・A14）**: 往復と往復の間は直列（第 k+1 回は第 k 回の改訂後の状態をレビューする）。往復の内側は、S2 の事実層・解釈層は作成の群（事実層 events／people／world、解釈層 逆算／動機と変容／テーマと感情／extras）ごと、S3 本文はページごと、あらすじは連続する章のまとまり（最大 6）ごとに、レビューと改訂を並行に呼ぶ（全幅、4.4「段内の並行」）。各呼び出しは自分の担当の要素を全体で、他の群・他層の要素を id／型／ラベルの参照として受け取る。指摘は対象の要素を持つ群へ、対象が無い指摘（`missing` など）は指摘したレビューの群へ回す。改訂の呼び出しが削除できるのは自分の群の要素だけ。改訂は群の固定順で適用する（結果が呼び出しの完了順に依存しない）。状態（agreed／revised／disputed）・未解決 `copied_phrase` の削除・advisory の決め方は 2 と同じ。

```jsonc
  "options": { "priority": "normal|high", "note": "" },
  "batch": null,                          // 一覧取り込み時は { "batch_id": "", "line": 12 }（4.5）
  "resolved": null,                       // 同定後に設定（4.6）: { "work_id", "title", "title_status": "confirmed|provisional",
                                          //   "method": "index_match|research", "source_ids": [], "alias_recorded": true, "resolved_at" }
  "state": "received"
}
```

- `work_query` は入力そのままを保持し、以後書き換えない。ジョブの対象は `resolved`（調査で確定した正式名称と `work_id`）で確定する（4.6）。

- 範囲の文法: `全体`／`N巻`／`N-M巻`／`N話`／`N-M話`／`第Nシーズン`／`「◯◯」編`／`劇場版`。省略時は `全体`。解釈できない入力は捨てずに `range_raw` を保持し、`clarifying` 状態で聞き返す。**（v1.5・CP-037）** 単位 `film`（「劇場版」「劇場版「◯◯」」）を追加。上の8形に加えて、第N巻・第N話・N巻-M巻・区切り（- 〜 ～ から 等）・全N話・シーズンN・第N期・『◯◯』編・◯◯編・漢数字・「、」「,」区切りの複数指定を受け付ける。解釈できない範囲は `range: null` とし、同定を走らせずに `clarifying`（reason `range_unparsed`）にする。
- **回答（v1.5・CP-037）**: 聞き返しへの回答は `sfsh answer <job_id> [--pick n] [--work t] [--medium m] [--range r]`（Discord は `/sfsh answer`）。`work_query` は書き換えず、回答は JobRequest の `answers[]` に残す。候補を選ぶ回答（`--pick`）は、既存作品ならその `work_id`、調査候補なら保存済みの出典から確定し、新しい検索をしない。
- 作品同定: 同名異作品・媒体違いが候補に挙がった場合は候補（題名・媒体・年）を提示して選ばせる。確定するまで本調査（S1）を始めない。候補が1件に定まる場合の自動確定と表記ゆれの扱いは 4.6。
- 範囲拡張は既存 `work_id` への追記として扱い、別作品にしない（公開モードは変えない）。

### 4.4 キュー管理 [決定]

- 状態遷移: `received → identifying → clarifying → queued → researching → structuring → generating → checking → building → built → publish_pending → published`。終端は `published / built（サイト開設前、または `publish.mode: manual` のとき、または自動公開の失敗時）/ failed / cancelled / held / merged`。承認待ちの状態は無い（5.3）。`publish_pending`（v1.9・A13）は「ビルド済み・公開待ち」で、自動公開が有効なときだけ通る（終端ではない）。
- 実体はディレクトリ移動（`inbox → ready → running → done|failed|held|cancelled`。`publish_pending` は `done/`）。状態変更は原子的なリネームで行い、全遷移を `logs/jobs/<job_id>.log` に追記する。
- 順序は優先度→受付順（空いた枠に次のジョブを入れる順。v1.9 で同時実行は最大 N、下の「並行実行」）。冪等キー = `work_id + range + schema_version`。同一キーの重複投入は既存ジョブへ合流させる。
- **並行実行（v1.9・AMENDMENT 13）[決定。並行数は暫定]**:
  1. **並行数**: worker は1プロセスで、その中の本処理スロットを最大 N 件同時に動かす。N は `harness/config/worker.json` の `max_concurrent_jobs`（既定 **3**、1〜8 の整数。不正な値なら worker は起動しない）。1回だけ変えるときは `sfsh worker --concurrency n`。**既定3の根拠**: ジョブの負荷はモデル呼び出し（CLI の子プロセス）と取得の待ちが中心で、待ちの間 CPU はほぼ空く。本機は 15.8 GB・8 論理プロセッサ。モデル CLI の子プロセスは実測で平均 約 80 MB（最大 約 0.7 GB、2026-11-23）、1ジョブが同時に出す呼び出しは段により 3〜6（claim 抽出・査読 3、あらすじの章 6）なので、3 ジョブで同時 9〜18 呼び出し・概ね 1〜2 GB に収まり、ブラウザや他の作業の余地が残る。API（CLI の利用枠）のレート制限に対しても同時呼び出しをこの程度に抑える。段の中の並行幅と合わせた全体の上限は下の「段内の並行」（v2.0）のグローバル上限で決まる。
  2. **本処理スロット**: 各ジョブは自分の `works/<work_id>/` と `logs/jobs/<job_id>.*` だけを書き、段の進め方・再試行・チェックポイントは単独実行と同じ。同じ作品の同じ範囲は冪等キーで合流するので、同じ作品を2つのスロットが同時に書くことはない。
  3. **受付レーン**: 同定（`identifying`）は1本のレーンで1件ずつ。受付済みの同定が終わるまで新しいスロットは起こさない（実行中のスロットは止めない）。スロットが1つのときは段の境目で同定を待つ（v1.5・M6 と同じ）。複数のときは境目で同定を起動だけして待たない。**聞き返し中（`clarifying`）のジョブは `inbox/` に留まり、枠を占有しない**。回答で `received` に戻り、同定のあと空いた枠で並行に処理される。
  4. **サイトのビルド**: 各ジョブの `building` は従来どおり行い、ビルド自体はビルドロック（`site/.input.lock`）で直列。
  5. **公開の直列化**: 自動公開が有効なとき（5.3）、ビルドを終えたジョブは `built → publish_pending` に移ってスロットを空ける（処理は止めない）。公開レーンは1本で、`publish_pending` のジョブを**ビルドを終えた順**（`publish_wait.order`＝ミリ秒の単調増加値）に1件ずつ公開する（`sfsh publish` と同じ関数。公開ロック `site/.publish.lock` の中でスナップショット作成→検証→push。プロセス間でも同時に走らない）。成功で `published`、失敗で `built`（4.4「完了後」）。別のジョブが compose から autocheck までの間（`gen/public.json` が書かれたが自動確認 5.1 が済んでいない）にいる間は、公開を待つ（未確認の作品を載せない）。完了通知は公開の後に1回だけ送る。
  6. **状態の持ち方**: 1ジョブ1ファイルは不変。`publish_wait {since, order, started_at}` は `publish_pending` の間だけ持つ（`started_at` は公開の実行中）。ジョブファイルの「読む→変える→書く」はすべてキュー状態ロック `queue/state.lock/`（mkdir による排他、所有者 `<pid>:<token>`、同一プロセス内は再入可、所有プロセスが死んでいれば引き継ぐ、保持はファイル操作の間だけ）の中で行う。worker の各スロット・CLI・Discord の runner・inbox への投入が同時に動いても、古い読み取りで新しい状態を上書きしない・同じジョブが2つのディレクトリに残らない・同じジョブを2つのスロットが走らせない。
  7. **rename の再試行**: Windows では、他プロセスが開いているファイルへの rename が一時的に失敗する（EPERM・EACCES・EBUSY。A13 の実測で `sfsh status` が runner の状態ファイルを読む瞬間に発生し、ジョブが failed になった）。原子的書き込みの rename はこの3種のときだけ短い間隔で再試行する（最大約2秒）。対象はキューのファイル・通知・runner の状態と予算・NKG・研究成果・work.json／INDEX。
  8. **取消**: 待ち中の `publish_pending` は取消できる（公開レーンは飛ばす）。公開の実行中（`started_at` あり）は取消できない。
  9. **回復**: worker の再起動時、実行中だったジョブは従来どおり `queued` に戻り、最初の未完了の段から続く。公開の実行中だった `publish_pending` は待ちに戻り、公開レーンがもう一度公開する。
  10. **Discord 側の起動（v1.9）**: 投入はいつでも受け付ける（runner の呼び出しごとに依頼ファイル `req-<id>.json`／結果 `res-<id>.json` が分かれ、ジョブ番号は排他的に予約される）。`start_worker` は worker が動いていなければタスク SFSHWORKER を起動し、動いていれば何もしない（動いている worker が空いた枠で拾う）。統括ジョブ（SFSHA*）の実行中でも起動を止めない（v1.8 までの制限は撤廃）。タスクは `worker --once` を待ち行列が空になるまで動かし、終了後にキューを再確認して、終了間際に入ったジョブがあればもう一度起動する。
- **段内の並行（v2.0・AMENDMENT 14）[決定。数値は暫定]**:
  1. **段ごとの並行幅**: `harness/config/parallel.json` の `stages`（段ごとの上書き）と `stage_width_default`（既定 **6**、1〜16 の整数）。不正な値はエラー（黙って既定に戻さない）。対象と意味: `claims`（claim 抽出のバッチ）、`claim_review`（claim 査読の1往復のバッチ。バッチの大きさは「その往復の件数 ÷ 幅」を 40〜120 件に丸めて、幅いっぱいに並ぶようにする）、`search`（粗筋枠・followup・gapfill の Luna 検索呼び出し。結果の処理と取得は優先順に直列のまま＝予算の会計と取得の順序が決定的）、`nkg_author`（S2 の作成の波の中の群）、`nkg_review`（S2 の往復の内側の群、3.3-8）、`write`（S3 本文のパートと往復の内側のページ）、`synopsis`（あらすじの章と往復の内側の章のまとまり）。段と段の間・作成の波の順・往復の順は依存なので直列のまま。
  2. **グローバル上限**: モデル CLI の子プロセス（Haiku＝`claude -p`、Luna＝`codex exec`）は、グローバル上限 `global_model_calls`（既定 **6**、1〜32）のスロットを持っている間だけ起動する。スロットは `logs/model-slots/slot-<n>/`（mkdir による排他、所有者 `<pid>:<token>`）で、worker の全ジョブ（A13 のジョブ並行は1プロセス内）と、別プロセスの `job resume`・`regen` の間で共有する。プロセス内は要求順（FIFO）、所有プロセスが死んだスロットは引き継ぐ。呼び出しのタイムアウトはプロセスの起動から数える（スロット待ちは含めない）。段の幅はその段が一度に求める数の上限で、実際に同時に動く数はグローバル上限で決まる（ジョブ並行 3 × 段の幅 6 ＝ 18 を求めても、動くのは 6）。
  3. **既定値の根拠**: **段の幅 6**: 1ジョブの段で同時に意味のある呼び出しは、S2 の群（事実層 3・解釈層 4）、本文のページ（5〜6）、あらすじの章（8〜15、6ずつ）、claim のバッチ（7〜9）、追加調査の対象（最大 6）で、6 あれば S2 と本文は全幅、残りも 2 波以内に収まる。**グローバル上限 6**: A14 の実測（2026-11-23、本機 15.8 GB・8 論理プロセッサ、ブラウザ・Discord などを開いた普段の状態）で、空きメモリ（Available MBytes）は着手時 約 1.5 GB、モデル CLI の子プロセスは 1 呼び出しあたり Haiku（claude.exe）約 200 MB（平均 201・最大 217 MB）、Luna（codex の node＋子）も同程度で、同時 3〜4 呼び出しの間に空きは最低 約 0.7 GB まで下がった（A13 の見積もり「平均 約 80 MB」は実測より小さかった）。上限 6 なら CLI は 約 1.2 GB で、空きを使い切らずに 1ジョブの段の全幅（6）が出る。A13 のジョブ並行（最大 3）と掛け算すると最大 18 を求めることになるが、動くのは 6 で、残りはスロット待ちになる（ジョブは遅くなるが PC は重くならない）。レート制限: Haiku は Claude Code CLI、Luna は Codex CLI の利用枠で動き、A14 の実測（同時最大 4〜6）で失敗・制限エラーは 0 件。空きメモリが多い PC や、上限を上げたいときは `global_model_calls` を上げる（PC が重いときは下げる）。数値は暫定で、実ジョブの並行運用の実測で見直す。
  4. **冪等性**: 段の出力は段の終わりに一括で書く（途中の部分結果は書かない）。並行の呼び出しの1つが失敗したら新しい呼び出しを起こさず、走行中の呼び出しがすべて終わってから段の失敗とする（`util/pool.ts`。write 段の本文‖あらすじも両方の終了を待つ）。段の自動再試行・`job resume --from` は段の最初からやり直すので、前の試行の呼び出しが残って二重に走る・状態を書き換えることはない。呼び出し単位の再試行（非ゼロ終了で1回）は従来どおり。
- **合流（v1.5・CP-037）**: 合流した重複要求は状態 `merged`（`queue/done/`、`merged_into` に合流先）で終わり、合流先の `merged_from[]` に記録された要求者にも以後の通知を送る。合流先に数えるのは failed・cancelled・merged 以外の同じキーのジョブと、キューのファイルを持たない M1〜M3 の旧ジョブ（`logs/jobs/<id>.state.json` が done）。範囲が違えば同じ作品でも別のジョブになる（例: 「全12話」で作った作品への範囲省略（全体）の指示。M6 の実測、CP-052）。
- 段ごとにチェックポイントを残し、異常終了後は最後に完了した段の次から再開する。自動再試行は段あたり2回まで、以後 `failed` として通知する。**（v1.5・CP-038）** これとは別に、モデル CLI の非ゼロ終了（使える出力なし）は呼び出し単位で1回だけ再試行する（5秒待ち。各試行は呼び出しログに1行ずつ）。
- **取消（v1.5・CP-037）**: `queued` 以前は即時に `cancelled`。実行中は次の段の境目で止まる（途中までの成果は残る）。
- **hold／release とキュー（v1.5・CP-038）**: hold された作品のジョブは次の段の境目で `held` になる。`release` はその作品の held のジョブを `queued` に戻し、worker が最初の未完了の段から続ける。
- `built` で止まった作品は、サイト開設時または次の `sfsh publish` 実行時にまとめて公開される。
- Restricted の作品に対する指示は受け付けるが、公開段へ進めない旨を即時返信する。
- `identifying`（同定調査 4.6）は短時間・小予算の段で、`queued` 以降の本処理より**先に**処理する。`clarifying` は聞き返しが必要な場合のみ通る。冪等キーの判定は `work_id` が確定する同定後に行う。**（v1.5・M6、CP-041 所見 a）** worker は実行中のジョブの各段の境目でも、受付済み・未同定の指示を同定する（聞き返し・合流・同定の通知の遅れは最大で実行中の1段分。M6 実測: 段の残り 46 秒で同定。改善前の M4 実測は約 33 分）。
- **完了後（v1.5・CP-037・M5）**: 実行器が done になったら worker がサイトをビルドして `building → built`。続けて、本番ゲートが開いていて（`publish.json` の `production_enabled: true`）`mode: auto` で `publish/` が初期化済みのときだけ `publish_pending`（v1.9）を経て、公開レーンが `sfsh publish` と同じ公開を行い、push と push 後検証が通れば `published`。公開に失敗してもジョブは `built` のまま（failed にしない）で、通知に失敗の要点を書く（`sfsh publish` で再試行）。

### 4.5 タイトル一覧の一括取り込み（バッチ）[決定・A02]

第3の入力系統として必須。1ファイル = 1バッチ、1行 = 1 JobRequest。取り込み後は単発指示と同じキュー・同じパイプラインを通る（バッチ専用の処理経路を作らない）。

- **入口**: `sfsh import <file> [--range <範囲>] [--medium <媒体>] [--priority] [--dry-run] [--origin muse|cli]`。Discord は `/sfsh import` の添付ファイル（4.2）。どちらも同じパーサを通す。`--dry-run` は解釈結果の一覧表示のみで投入しない。
- **テキスト形式（.txt）**: 1行1タイトル。行全体を題名として扱う（範囲は行内に書かない）。前後の空白は除去、空行と `#` 始まりの行は無視。
- **CSV 形式（.csv）**: 1行目はヘッダ必須。列は `title`（必須）, `range`, `medium`, `note`, `priority`（任意）。RFC 4180 の引用符規則。未知の列は無視して警告。`range` は 4.1 の範囲文法。
- **既定値**: 行に範囲・媒体が無ければコマンドの `--range`／`--medium`、それも無ければ `全体`／`null`。
- **文字コード**: UTF-8（BOM 可）を厳密に試し、失敗したら CP932（Shift_JIS）で読む。どちらでも読めなければファイル全体を拒否し、1件も投入しない。採用した文字コードを batch.json に記録する。
- **上限**: 1ファイル 200 行まで [暫定・U-18]。超過はファイル全体を拒否する（黙って切り捨てない）。
- **バッチ記録**: `queue/batches/<batch_id>/` に元ファイルの写しと `batch.json`（各行の行番号・入力表記・`job_id`・状態・確定した正式名称）を置く。`batch_id` は `B<日付>-<連番>`。
- **行の独立性**: 行ごとに独立したジョブとし、1行の失敗・聞き返し・Restricted が他の行を止めない。解釈できない行（空の `title`、不正な `range`）は投入せず batch.json にエラーとして残し、残りは進める。
- **重複**: ファイル内で構文正規化（4.6-1）後に同一の行は1ジョブに合流。同定後に同じ `work_id`＋範囲になった行、および既存ジョブ・既存作品と同じ冪等キーの行も合流する（4.4）。合流は batch.json に記録する。
- **順序**: まず全行の同定調査（`identifying`）を済ませ、聞き返しと合流を早期に確定させてから、行番号順（優先度が同じ場合）で本処理に入る。本処理は空いた枠から並行に進む（v1.9・4.4「並行実行」。v1.8 までは同時実行1）。
- **通知**: 受付時に件数、同定完了時に「確定／表記を正式名称へ補正／聞き返し中／エラー」の内訳と補正一覧、全行終端時に結果集計を、1バッチにつき各1通で `reply_to` へ返す（行ごとに通知を乱発しない）。聞き返しは1通にまとめる。照会は `sfsh status --batch <batch_id>`。取消は `sfsh cancel --batch <batch_id>`（未完了行のみ）。
- **扱いは単発と同じ**: バッチで投入した作品も Public 既定で、自動確認（5.1）を経て公開まで進む。予算は各ジョブが 1.3 の上限を個別に持つ。バッチ総額・月額の上限は U-13 の回答に従う。
- `note` 列と元ファイルは非公開領域にのみ置く。

### 4.6 正式名称の正本化とエイリアス [決定・A02]

入力された題名は「検索語」であり、作品の題名ではない。**題名の正本は調査で判明した正式名称**とし、入力表記はエイリアスとして残す。

1. **構文正規化（決定的）**: 入力を NFKC 正規化し、前後空白除去・連続空白の圧縮を行ったものを照合キーとする。`work_query` 自体は書き換えない。
2. **既存台帳との照合**: 照合キーを `works/INDEX.json` の `title`／`title_original`／`title_reading`／`aliases[].text` と比較する。1作品だけに一致すればその `work_id` で確定（`method: index_match`）。複数作品に一致すれば候補提示（4.1）。
3. **同定調査**: 一致が無ければ、小予算のウェブ調査 [暫定: 検索5回・取得8ページ、ジョブ予算に算入] で候補（正式名称・媒体・作者・初出年・根拠出典）を Luna が抽出し、以降の判定はコードが行う。モデルの記憶だけを根拠にした候補は棄却する（C-7）。
4. **正式名称の定義**: T1 出典（出版社・公式サイト・書誌DB）が表記する題名。サイト言語（U-17、既定は日本語）での公式題名がある場合はそれを `title`、原語の題名を `title_original` とする（海外作品の扱いは [未決 U-19]）。副題・巻次・「劇場版」等は題名に含めず、範囲（`coverage`）で表す。
5. **確定規則**:
   - 候補が1件（`medium_hint` で1件に絞れる場合を含む）→ 聞き返さずに自動確定し、入力表記と異なる場合は「入力『X』→ 正式名称『Y』」を通知する。
   - 候補が複数 → `clarifying` で候補提示。候補なし → `clarifying` で再入力を求める（`failed` にしない）。
   - 根拠が T1 1件以上または独立した T2 2件以上なら `title_status: confirmed`。それ未満は `provisional` とし、処理も公開も進める。advisory に載せ（5.2）、後から根拠が得られれば `confirmed` に上げる。
6. **エイリアスの記録**: 照合キーが正本題名と異なる入力表記は、略称・通称・打ち間違いの別なくすべて `work.json` の `aliases[]` に追加する。調査で見つかった別名（旧題・公式略称・通称）も同じ配列に入れる。重複は合流し、削除はオーナー操作のみ。
7. **表記の統一**: NKG（`work.title`）、台帳、キュー・通知、サイト（ページ題名・一覧・パンくず・サイトマップ）はすべて正本題名を使う。入力表記を題名として表示する箇所を作らない。
8. **題名の訂正**: 後から正本題名を改める場合、旧題名はエイリアスに移し、`work_id`（＝公開 URL）は変えない。題名変更は再ビルドで反映する。同定そのものが誤り（別作品）だった場合は訂正ではなく、旧作品を `takedown`／`purge` して新規作品として作り直す。

**作品台帳の題名項目（`works/<work_id>/work.json`）**

```jsonc
{
  "work_id": "", "title": "正本題名", "title_original": "", "title_reading": "ひらがな読み（索引の並び順・検索用）",
  "title_status": "confirmed|provisional", "title_source_ids": [],
  "aliases": [ { "text": "", "kind": "official_alt|common|input", "attested": false, "source_ids": [],
                 "origin_job_id": "", "first_seen": "ISO8601" } ],
  "medium": "", "creators": [], "genres": [], "tags": [],          // genres・tags は 6.5 の統制語彙
  "first_published_at": null, "updated_at": null                    // 公開サイト上の初回公開・最終更新
  // 以下 v1.0 どおり: 権利状態・公開モード・history[] ほか
}
```

- `kind`: `official_alt` = 公式の別題・旧題・公式略称／`common` = 出典で確認できる通称／`input` = 入力表記（略称・打ち間違いを含む）。`attested` は出典で確認できたかどうか。`input` でも出典で確認できれば `common` に昇格させる。
- `title_reading` は書誌DB等の出典があればそれを使い、無ければモデル推定とし推定である旨を記録する（並び順と検索にのみ使い、事実として表示しない）。
- エイリアスは1件80字以内・1行。題名・名称であり原作の表現ではないが、公開物に入るため 6.3-4 の検証対象とする。
- `works/INDEX.json` は各作品の `work_id, title, title_original, title_reading, title_status, aliases, medium, creators, genres, tags, publish_mode, first_published_at, updated_at` を持つ（`work.json` からの自動生成。手で編集しない）。
- **公開側での扱い**: エイリアスは全件を検索インデックスに入れる（6.5）。作品ページに「別名」として表示するのは `attested: true` のものだけとし、未確認の入力表記・打ち間違いは表示しない。

## 5. 権利まわりの確認と取り下げ（軽量）[A06]

公開前に置くのは、軽量な自動確認と advisory だけ。**人手承認は置かない。作品を止める判定はしない**（P-1）。問題が出たら公開後の取り下げで受ける。

### 5.1 自動確認（S4。決定的コード）[決定]

機械的に判定できる C-2 違反だけを扱う。該当しても**作品は止めず、該当箇所だけを直して先へ進む**。

| ID | 検出するもの | 処置 |
|---|---|---|
| A-1 テキスト混入 | 生成文と、保存済みの出典抜粋（1.3。原作の引用を含みうる）との連続一致 [暫定: 30字以上。固有名の許可リストに一致する部分は除く] | 作成モデルが該当文を1回書き直す → なお一致する文は削除して続行 |
| A-2 画像・メディア混入 | ビルド物に、自作図版（コード生成の SVG）以外の画像・音声・動画、または外部メディアの埋め込み・ホットリンクがある | 該当ファイル・参照を除去して再ビルド。除去できない場合のみビルド失敗（実装不具合として扱う） |

- 限界: ハーネスは原作本体を持たない（1.2-6）ため、原作そのものとの照合はできない。**これ以上の検査は足さない。** 補うのは 3.3 のレビュー指摘（`copied_phrase`）、5.2 の advisory、5.4 の取り下げ。

### 5.2 advisory（助言表示）[決定]

`check/report.json` に記録し、完了通知に件数と要点を添える。**通過・停止には使わない。** オーナーが見て気になれば `hold`／`takedown`、または修正ジョブを出す。

- 長い引用形がある（鉤括弧の中が文になっているもの）[暫定: 20字以上]
- 出典抜粋との文単位の類似が高い [暫定: n-gram 類似度 0.5 超]
- レビューで未解決の `too_concrete`（場面の再話に近い）
- 対象が歌詞・詩・ごく短い作品（抽象化しても表現に近づきやすい）
- 調査の過程で、権利者が要約・解説の公開を明示的に禁じる方針を見つけた（積極的に探す工程は置かない）
- 題名が `provisional`（4.6）
- 件数・文字数が目安を超えた（2.4）

### 5.3 公開モードと流れ [決定]

公開モードは2値。**作る側に倒した既定**とする。

| モード | 意味 | なる条件 |
|---|---|---|
| **Public** | ビルドと公開の対象 | **既定**。新規作品・範囲追加・再生成のすべて |
| **Restricted** | ビルドから除外（既公開分は取り下げ） | オーナーの `hold`／`takedown` のみ。`release` で Public に戻る |

```
S3 生成 → S4 自動確認（A-1・A-2。該当箇所のみ修正）＋ advisory 記録 → S5 ビルド → S6 公開 → 完了通知（advisory 要点つき）
```

- **撤去（v1.2）**: Review モード、「新規作品は必ず Review から」、3層チェック（H-1〜H-7、S-1〜S-6、人手チェックリスト7項目）、内容ハッシュ単位の承認と承認無効化、自動で Restricted に落とす条件 (a)〜(f)、`approve`／`reject`、`awaiting_approval`。
- 著作権保護期間の内外で扱いを変えない。
- サイト開設（初回 push。U-05）の後は、S6 まで自動で進む（`publish.mode: auto` が既定）。`manual` にするとジョブは `built` で止まり、オーナーの `sfsh publish` でまとめて公開する（U-07）。開設前は全ジョブが `built` で止まる。
- **設定ファイル（v1.5・M5、開設時の値は CP-048）**:
  - `harness/config/publish.json`: `production_enabled`（本番ゲート。開設の指示で `true` にした）、`remote_url`（`https://github.com/kokuren333/sfsh-site.git`）、`base_url`（`https://kokuren333.github.io/sfsh-site/`）、`mode`（`auto`）、`test_remote_url`（`publish-test/site.git`）、`commit_author`（`SFSH publisher <sfsh-publisher@users.noreply.invalid>`）、`url_check`（`timeout_s` 600・`interval_s` 15）、`allow_emails`（空）。ゲートが閉じている間、push 先はローカルの試験用 bare だけで、git もネットワーク転送を拒否する設定で動く。
  - `harness/config/site.json`: `site_name`（v1.6・A10 で `"SFSH"`。`null` の場合の表示も「SFSH」。U-14）、`contact`（`{ kind: "issues", url: "https://github.com/kokuren333/sfsh-site/issues" }`。U-10）。厳格に検証し、メール様の値・http・改行・`<>` を拒否する。
- **`published` への遷移（v1.5・M5）**: 4.4 の「完了後」のとおり（ゲート開・`auto`・`publish/` 初期化済みで、push と push 後検証が通ったとき）。リリースごとの監査記録 `works/<id>/releases/<release_id>.json` は内容が変わった作品だけに S6 が書く（ビルドの入力条件は「Public かつ `gen/public.json` あり」で、公開記録には依存しない）。
- リリースごとに `releases/<release_id>.json`（内容ハッシュ・モデルID・advisory 件数・日時）を残す。監査と取り下げのための記録であり、承認記録ではない。
- ローカルプレビュー（`sfsh preview`）は本機内でのみ閲覧可能とし、外部ホスティングしない。
- `hold`・`release`・`takedown`・`purge` の全記録（誰が・いつ・何を理由に）を `work.json` の `history[]` と `logs/LEDGER.md` に残す。

### 5.4 差し止め・取り下げ [決定]

問題対応の主経路。速く・確実に・痕跡を残さず消せることを要件とする。

| 操作 | 用途 | 動作 | 目標時間 [暫定] |
|---|---|---|---|
| `hold` | 公開を止めたいとき | Restricted に変更、進行中ジョブを `held` へ。既公開なら次のビルドで外れる | 即時 |
| `release` | hold の解除 | Public に戻し、次のビルドで公開 | 即時 |
| `takedown` | 既公開物の撤去 | Restricted に変更 → 当該作品を除いて再ビルド → push 前検証 → 公開リポジトリへ snapshot push（6.3 により履歴にも残らない）→ 公開 URL が 404 であることを確認 → 台帳記録 | 指示から15分以内 |
| `purge` | 完全消去の要請時 | takedown に加え、ローカルの `gen/` と `releases/` を削除（`research/` と台帳の記録は証跡として保持） | — |

- takedown はオーナーの指示だけで即時実行する（確認の往復を挟まない）。
- 権利者などから申し立てを受けたら、**是非を検討する前にまず takedown** し、その後で判断する。
- サイトに取り下げ依頼の窓口ページを置く。連絡先は U-10（公開の前提条件にはしない）。
- 検索エンジンのキャッシュ、GitHub 側に残る旧コミットの完全消去は SFSH の外の手続きになる。手順を運用手順書に記載する（M5 成果物）。
- takedown の実地確認は M5 関門で1回行う（定期訓練は義務にしない）。

## 6. GitHub Pages 公開の設計

### 6.1 境界線 [決定]

| 公開リポジトリに**含める** | **含めない**（非公開ハーネス側にのみ存在） |
|---|---|
| ビルド済み HTML / CSS / JS（同梱ライブラリ含む） | ハーネス本体コード、プロンプト、設定、ジャンルプロファイル |
| 作品ごとの `public.json`（公開射影）とそこから生成した自作 SVG | `nkg.json` 全量、`research/`（取得ページ・抜粋・claims）、`check/` 報告、レビュー経緯 |
| 出典一覧（題名・発行者・URL・参照日・ライセンス表示） | Restricted の作品に関する一切（題名を含む） |
| サイト共通ページ: このサイトについて／方針（非公式・独自分析・引用しない旨）／権利者向け窓口／ネタバレ注意 | 台帳（LEDGER、work.json の履歴）、キュー、ジョブログ、モデル呼び出しログ |
| `.nojekyll`, `robots.txt`, `404.html`, サイトマップ、`release-manifest.json`（公開ファイルのハッシュ一覧のみ）、`catalog.json`（Public 作品の検索・索引用データ。6.5） | `.env`、トークン、鍵、Discord 設定、個人情報、ローカルパス |

- サイト内の画像は自作図版のみ。書影・場面写真・公式ロゴ・キャラクター画像・それらを模した生成画像は載せない。外部画像の埋め込みもしない。
- 各作品ページに常設する表示: 非公式である旨、対象範囲、ネタバレ度、出典、認識区分（確定設定／一般的解釈／考察／独自分析）の凡例、情報不足の観点。

### 6.2 サイト構成 [決定]

- トップ（検索窓・新着・ジャンル入口。6.5）／作品索引 `/works/`／ジャンル別・媒体別一覧（6.5）／作品ページ（概要・対象範囲）／可視化ページ: **A 動的人物関係図**（フェーズ切替で関係と意味が変わる）、**B リバースプロット**（結末→直接原因→要因→根本原因の木）、**C 情報の非対称性マトリクス**（秘密×人物＋読者、フェーズ切替。M05 有効時のみ）／テーマ・批評／文化的文脈／解釈の分岐／理解度テスト／出典。
- 既定の入口はリバースプロットと人物関係図とし、場面順の通読型ページは作らない（C-3）。**（v1.7・A11）例外**: 作品ページの「あらすじ（全編・ネタバレ）」（3.2）は冒頭から結末までを時系列に要約して語り直す。場面・台詞の再現はしない。時系列（M04）は主要 Event のみの二重軸図として出す。
- 結末を含む内容は既定で折りたたむかどうか [未決 U-11]。（v1.7・A11）あらすじ（全編・ネタバレ）は例外として折りたたまず、冒頭のネタバレ注意で明示する（BRIEF AMENDMENT 11「冒頭にネタバレであることを明示する」。全文を折りたたむとページの本文が隠れるため）。

### 6.3 「サイトのみ push」の実現方式 [決定]

1. **別リポジトリ方式**。ハーネスの作業リポジトリは remote を持たない（U-06。v1.5 で確定）。サイト用公開リポジトリは `publish/` に置いた独立クローンで、ハーネスのリポジトリと履歴・リモートを共有しない。サブモジュール・サブツリー・同一リポジトリの別ブランチは使わない（誤 push の経路を作らないため）。ハーネス本体の公開は 6.6 の別経路で行う。
2. **許可リスト方式のビルド**。S5 は `works/INDEX.json` から「Public かつリリースあり」の作品だけを列挙し、その `gen/public.json` だけを読む。それ以外のパスを読むコードを書かない。
3. **公開は単一コマンド `sfsh publish` のみ**。サイト用リポジトリへの push 権限（資格情報）を使うのはこのコマンド（と同じ関数を呼ぶ worker の自動公開・`takedown`・`purge`）だけとし、他の段・モデル呼び出しからは push できない構成にする。**（v1.5）** コード上で `git push` を実行するのは `harness/src/publish/repo.ts`（サイトのスナップショット）と `harness/src/publish/harnessExport.ts`（6.6）の2か所だけで、テストで保証する。
4. **push 前検証（(f) 以外の全項目合格で push。いずれも機械判定できる実害項目。P-1）**: (a) `dist/` の全ファイルが拡張子許可リスト内（html, css, js, json, svg, txt, xml, woff2, ico）／(b) `dist/` に現れる全 `work_id` が Public（Restricted が混ざっていない）／(c) 秘密情報スキャン（トークン様文字列、メールアドレス、`C:\` 等のローカルパス）に該当なし／(d) 外部リソース参照なし／(e) 自動確認 A-2（5.1）を `dist/` に対して再実行して該当なし／(f) ファイル数・総容量の前回比の異常増は警告のみ（止めない）／(g) `catalog.json` と一覧系ページに現れる作品が (b) の Public 集合と完全一致し、項目が 6.5 の許可項目のみで、題名・エイリアス・タグが (c) に該当しない。
5. **スナップショット公開**。公開リポジトリは常に「現在の `dist/` だけを含む単一コミット」とし、毎回履歴を持たないコミットで置き換える（強制 push）。取り下げた内容が公開履歴に残らない。公開の監査証跡は非公開側の `works/*/releases/` と `logs/LEDGER.md` に持つ。強制 push の対象はこの公開リポジトリのみで、ハーネスが専有する。
6. **push の実行**: 作品ごとの人手承認は無い。サイト開設（リポジトリ作成・Pages 有効化・初回 push）だけはオーナーの指示で行う [U-05]。開設後は push 前検証に通れば自動で push する（`publish.mode: auto`。5.3）。**（v1.5・M5）** 開設前は本番ゲート（`publish.json` の `production_enabled: false`）で、push 先をローカルの試験用 bare `publish-test/site.git` に限る。開設の指示（2026-11-23 10:19）でゲートを開けた。検証とコミットは dist の写し `site/.publish-stage/` に対して公開ロックの中で行う。
7. 公開後検証: 公開 URL を取得し、`release-manifest.json` のハッシュと一致することを確認して台帳に記録する。**（v1.5・M6）** 取得の前に Pages のデプロイ完了を待つ: `release-manifest.json` をキャッシュ回避のクエリつきで取得し、新しいマニフェストと一致するまでは正規の URL を取得しない（デプロイ前に新しいファイルを取得して CDN に 404 がキャッシュされるのを防ぐ。開設時の実測: 76 中 2 件が 20 分超 404 のまま。CP-048）。時間内にデプロイを観測できなければ正規 URL を取得せずに失敗とする（`publish verify-url` で後から確かめる）。
8. **ハーネス側リポジトリの管理境界（A01 補強）**: 2リポジトリ分離は必須要件であり、単一リポジトリへの統合案は不採用とする。
   - ハーネス側リポジトリ（`sfsh/` 直下で git 管理）が持つもの: `harness/`, `design/`, `logs/`, `site/src/`, `works/`（NKG・`research/`・`gen/`・`check/`・`releases/`・`work.json`）, `queue/`, `BRIEF.md`。
   - ハーネス側でも git 管理しないもの（`.gitignore`）: `.env` と資格情報、`publish/`（Pages 側リポジトリの独立クローン。入れ子として取り込まない）、`site/dist/`（再生成可能）、`node_modules/`、`research/raw/` の取得ページ本体（保持はローカルのみ。出典カードとハッシュは管理する）。
   - **（v1.5・A08）** ハーネス側の作業リポジトリには remote を置かない（U-06 確定）。Restricted の作品と出典抜粋を含み、履歴ごとは公開できないため（全コミットが `works/`・`logs/`・`queue/`・`_handoff/` に触れる。CP-047）。ハーネス本体は 6.6 の書き出しで別の公開リポジトリへ出す。
   - Pages 側リポジトリが持つのは `site/dist/` の写しだけで、6.1 の「含める」欄以外のファイルが1つでもあれば push 前検証 (a) で止める。
   - **取り違え防止**: `sfsh publish` は push 直前に、`publish/` の remote URL が設定済みの Pages 側リポジトリと一致し、かつハーネス側の remote と異なることを検査する。不一致なら中止する。ハーネス側の作業ツリーからは Pages 側リモートを登録しない。

**構造化図示の共通基準**

- ラベルは常時表示し、ホバーしなければ読めない情報を作らない（ホバー・タップは補足のみ）。凡例を図のすぐ近くに常設する。
- 配置はビルド時に決定的に計算した静的レイアウトとし、表示のたびに動く・揺れる配置（物理シミュレーションの常時実行）は使わない。
- フェーズ切替は離散的なボタン／タブで行う（連続再生のタイムラインにしない）。
- すべての図に、同じ内容の**表またはリストによる代替表示**を同じページに置く（一覧性とアクセシビリティの担保）。

| 図 | 基準 |
|---|---|
| A 動的人物関係図 | 既定表示は主要人物12名まで [暫定]、残りは「全員を表示」で展開。**ノードの位置はフェーズを切り替えても動かさず**、変わるのは関係（線・ラベル）だけにする。線のラベルは関係の種類を短く（10字以内）。変化した関係は切替時に強調する。 |

### 6.5 発見可能性: 検索・索引・絞り込み [決定・A04]

**見たい作品にすぐたどり着けることは必須要件**とする。目標: 任意の Public 作品に、サイト内のどのページからでも2操作以内（検索語入力→結果を選ぶ／索引を開く→作品を選ぶ）で到達できる。すべて静的サイトの範囲で実現し、外部の検索サービス・サーバー処理・解析は使わない（1.2-7）。

**カタログデータ**

- S5 が `works/INDEX.json` から `dist/catalog.json` を決定的に生成する。対象は「Public かつリリースあり」の作品のみ（6.3-2 と同じ許可リスト）。
- 項目（これ以外を入れない）: `work_id, url, title, title_original, title_reading, aliases[]（表記のみ）, medium, creators, genres, tags, status（完結／連載中／不明）, first_release_year, coverage_label, spoiler_max, has_matrix（C の有無）, first_published_at, updated_at`。
- 本文・分析文・出典抜粋・`note`・Restricted 作品の情報は入れない。`takedown` 時は同じ再ビルドで catalog・一覧ページ・サイトマップから同時に消える。

**サイト内検索**

- 方式: `catalog.json` を読み込み、ブラウザ内で照合するクライアントサイド検索。検索窓を全ページのヘッダに置く。
- 検索対象: 題名、原題、読み、**エイリアス全件**（4.6。未確認の入力表記・打ち間違いを含む）、作者名。本文の全文検索は v1 の対象外（ネタバレが検索結果に露出するため）。
- 照合: 検索語と対象の双方を同じ規則で正規化して部分一致させる。正規化 = NFKC、英字の小文字化、カタカナ→ひらがな、空白・記号・長音符の除去。正規化後4字以上の検索語には、題名・エイリアスに対する編集距離1の一致も許す [暫定]。
- 順位: 題名の完全一致 ＞ 題名の前方一致 ＞ 題名の部分一致 ＞ エイリアスの完全一致 ＞ エイリアスの部分一致 ＞ 読み・原題 ＞ 作者名 ＞ あいまい一致。同順位は題名の読み順。
- 表示: 結果は**正本題名**で表示し、媒体・対象範囲を添える。エイリアスで一致した場合は「『（入力語）』に一致」と添えるが、エイリアス自体を題名のように表示しない。入力ごとに逐次更新し、1入力あたり 100ms 以内 [暫定]。0件のときは索引とジャンル一覧へのリンクを出す。
- 検索語は URL（`?q=`）に反映して共有・再訪できるようにする。検索語をどこにも送信・記録しない。
- 規模の前提: 1,000作品・`catalog.json` 圧縮後 300KB まではこの方式（全件走査）で足りる [暫定]。超える見込みが出た時点でインデックス分割を PM に提案する。

**作品一覧／索引**

- 索引ページ `/works/`: Public 全作品を静的 HTML の一覧として出力する（JS が無くても全件にたどり着ける）。既定の並びは題名の読み順（五十音→英字→数字）で、行見出し（あ・か・さ…／A–Z／0–9）へのジャンプを置く。
- 並び替え: タイトル順／追加順（`first_published_at` の新しい順）／更新順。切替はクライアント側、状態は URL に反映する。
- 一覧の1行に出すもの: 正本題名、媒体、作者、ジャンル、対象範囲、ネタバレ度。書影などの画像は出さない（6.1）。
- トップページ: 検索窓、新着（追加順の先頭12件 [暫定]）、ジャンル・媒体の入口、索引へのリンクで構成する。

**絞り込み**

- 軸: 媒体／ジャンル／タグ／完結状況／初出年代（10年刻み）／可視化の有無（C マトリクスあり）。同じ軸の中は OR、軸どうしは AND。各選択肢に該当件数を出し、0件になる選択肢は選べなくする。検索語との併用可。状態は URL に反映する。
- ジャンルとタグは**統制語彙**とする（`harness/config/genres.json`, `tags.json`）。語彙に無い語は付けない。ジャンルは 2.5 のジャンルプロファイルと同じ語彙を使う。タグは作品あたり8個まで [暫定]、Luna が調査結果から提案し Haiku がレビューする（3.2）。語彙の追加はオーケストレーターが台帳に記録して行う。
- タグは作品の属性（題材・舞台・形式・受賞など）を表す語に限り、展開や結末を明かす語（ネタバレになるタグ）を語彙に入れない。
- ジャンル別 `/genres/<slug>/`・媒体別 `/media/<slug>/` の一覧ページを静的 HTML として出力する（JS なしでも使える絞り込みの入口。件数0のページは出力しない）。作品ページからは該当するジャンル・媒体・作者の一覧へリンクする。

## 7. マイルストーンと関門

### 7.1 運用規則 [決定]

- 関門判定は PM（Fable 5.2）のみが行う。オーケストレーターは各関門で `logs/gates/M<n>.md`（合格基準ごとの証拠: コマンド、出力、ファイルパス）を提出する。証拠のない「完了」は不合格。
- **合格基準は客観的に判定できる項目だけ**（コマンド出力・テスト結果・ファイルの有無・計測値）とする（P-1）。見た目や文章の質などの主観評価は「所見」として記録して改善に回し、関門を止めない。**発注者の確認待ちを関門条件にしない。**
- オーケストレーターは作業パッケージ（WP）単位で実働部隊へ発注する。WP は「入力／成果物／受入条件」を持ち、1つの WP は1つの関門にのみ属する。
- マイルストーンは順に進める。ただし関門判定を待つ間、次のマイルストーンの WP に着手してよい。不合格が出たら該当 WP の修正を優先する。節目ごとに `logs/LEDGER.md` へ追記する。
- 発注者の指示を要するのは次の3つだけ: (1) C-2・C-8 に触れる設計変更／(2) 公開リポジトリの作成と初回 push（U-05）／(3) Discord bot の本番サーバー接続（U-04）。暫定値の変更、スキーマの型追加（原文・台詞を格納する型を除く）、ライブラリ選定は、オーケストレーターが決めて台帳に記録する。
- 試験作品はオーケストレーターがジャンルの異なるものを選び、台帳に記録する（U-12）。著作権保護期間の内外による制限は設けない。

### 7.3 非機能目標 [決定・v1.4。M2 の実測（CP-027〜029）で確定]

いずれも目標値であり、ジョブの停止条件にしない（P-1-5）。

- 1ジョブ（1作品・標準範囲）: 指示から公開（開設前は `built`）まで **45分以内**。超過は advisory として記録する。実測（M2・S0〜S3）は段合計 28分27秒、解釈層のばらつきの上側で約36分。短縮策（解釈層・claim 抽出の並列化）は任意の改善で、関門条件にしない。M6 の WP-6.2 で3作品の実測と並べて再確認する。
- 再現性: 同一入力・同一出典（保存済みの claim と出典カード）で S2 以降を再実行したとき、**スキーマ検証の合否と、決定的な確認の結果**が変わらない。対象は: 検証 ok／errors 0、出典なし要素 0、出典カード外の出典 0、`authored_by = reviewed_by` 0、信頼度の再計算不一致 0、追跡違反 0、自動確認 A-1・A-2（5.1）の適用後に公開物へ残る検出 0。**生成内容（要素数・gaps・公開対象数・フェーズ分割・警告件数）の一致は求めない**（LLM の揺れは許容し、差は所見として記録する）。関門での確認は 7.4 M3。
- 費用: 1ジョブのモデル費用の目安は 1.00 USD、月額の目安は 50 USD（U-13。発注者の回答で置き換える）。超過は advisory。
- 可観測性: すべてのジョブが、どの段で・どのモデルが・何を根拠に・いくらで処理したかを後から追える。

## 付記: 本書で確定したことの要約（v1.8）

1. 権利面で守る核は1つ: 原作の文章・台詞・画像を再利用しない（C-2）。それ以外は「ゲートで創造性を落とさない」（P-1）に従い、迷ったら作る側に倒す。
2. 公開前にあるのは自動確認2項目（テキスト混入・画像混入。該当箇所だけ直す）と advisory だけ。人手承認・Review モード・ハッシュ単位承認は無い。問題は取り下げ（15分以内）で受ける。
3. 公開モードは Public（既定）／Restricted（オーナーの hold・takedown のみ）の2値。
4. 調査は Luna 系（`gpt-6-luna`、`gpt-6.2-luna` が使えれば優先）、デザインと執筆は Haiku（`claude-haiku-5-5`）。レビューは常に逆側。調査の本文取得だけは決定的コードのフェッチャが行う（robots・denylist・予算の強制）。モデル呼び出しは CLI 経路。
5. ハーネスの作業リポジトリ（ローカル・remote なし）と公開サイト（`kokuren333/sfsh-site`）は別リポジトリ。サイト側は `dist/` の単一コミットだけを持つ。ハーネス本体は許可リストで書き出した写しを別の公開リポジトリ `kokuren333/SFSH`（Apache-2.0）に出す（6.6）。
6. NKG はフェーズ単位で、場面・台詞を表す型を持たない。全要素に出典・決定的に計算した信頼度・認識区分が付く。件数・文字数は目安。
7. 指示は Discord・CLI（Muse）・タイトル一覧（.txt／.csv）から同一形式でファイルキューに入り、1つの worker が最大 N 件（既定3）を並行に、段ごとに再開可能な形で処理する（v1.9）。題名の正本は調査で判明した正式名称。
8. サイトと図は「見やすくシンプル」かつレスポンシブ（スマートフォン／タブレット／PC）を数値基準つきで必須とし、検索・索引・絞り込みを静的サイト内で提供する。入口とナビゲーションは ChatGPT の説明 UI に寄せたカード・チップ（A09）。図表はどの幅でも図として表示し、スマートフォン幅（360／390px）でも横スクロールや縮小に頼らず読める（図のルール、v1.6）。本文は連続した散文で書く（執筆仕様 v2、v1.6）。作品ページの本文の中心は、NKG の事実層から冒頭から結末までを時系列に語り直す「あらすじ（全編・ネタバレ）」（v1.7・A11。素材にない細部は書かない）。サイト名は「SFSH」。
9. 関門は客観的に判定できる項目だけで判定し、発注者の確認待ちを条件にしない。発注者の指示を待つのは、公開リポジトリの作成・初回 push と bot の本番接続だけ。
10. （v1.8・A12）調査はカバレッジ駆動。粗筋（出来事）の素材を分析とは別枠で集め、claim と事実層の両方で決定的に不足を検出して、不足だけを狙う追加調査を予算（40／60／30分、上限は不変）の範囲で回す。届かない目標は情報不足として記録する。
11. （v1.9・A13）ジョブは並行に進む（既定3件、`harness/config/worker.json`）。共有するキューの状態はロックの中でだけ書き換え、サイトのビルドと公開は1件ずつ。公開はビルドを終えた順に1本のレーンで行い、待っている間の状態は `publish_pending`（ビルド済み・公開待ち）。聞き返し中のジョブは枠を使わない。連投・統括ジョブの実行中の投入も受け付ける。
12. （v2.0・A14）1ジョブの段の中も並行に進む。段ごとの並行幅は `harness/config/parallel.json`（既定6）。レビューの往復の内側は群／ページ単位で並行、往復の間は直列。モデル呼び出しの同時数はジョブ・プロセスをまたいだグローバル上限（既定6）で抑える。
